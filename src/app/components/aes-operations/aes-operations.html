SubBytes Transformation

Non-linear byte substitution using the S-Box lookup table

How It Works

SubBytes is a non-linear substitution step where each byte in the state is replaced with another according to a fixed 16x16 lookup table called the S-Box.

For a byte value, the upper nibble (4 bits) selects the row and the lower nibble selects the column. The value at that position becomes the output.

Substitution Process
Input: 0x{{ toHex(subBytesInput()) }}
Row: {{ subBytesResult().row.toString(16).toUpperCase() }} (upper nibble)
Column: {{ subBytesResult().col.toString(16).toUpperCase() }} (lower nibble)
Output: 0x{{ toHex(subBytesResult().output) }}

Why this specific substitution table?

The AES S-Box is not a random table. It is mathematically constructed for maximum cryptographic strength. The S-Box is built in two steps:

Step 1: Multiplicative inverse in GF(2⁸)

For each byte b, compute its multiplicative inverse b⁻¹ in the Galois field GF(2⁸), such that b × b⁻¹ = 1. Zero maps to zero (it has no inverse). This provides maximum non-linearity — the inversion function over a finite field has the best resistance characteristics against differential and linear cryptanalysis.

Step 2: Affine transformation

The inversion result is passed through an affine (linear + shift) transformation over GF(2). This eliminates fixed points (bytes that would map to themselves) and makes the S-Box asymmetric. Without the affine transform, the S-Box would have algebraic structure exploitable by attacks.

Why not a random table?

A random table may have weaknesses: linear approximations, high-probability differential characteristics, fixed points. The AES S-Box construction provably guarantees:

  • Maximum non-linearity (112 out of 120 possible)
  • Low differential uniformity (= 4)
  • No fixed points (S(x) ≠ x for all x)
  • No opposite fixed points (S(x) ≠ x̄ for all x)

ShiftRows Transformation

Cyclical byte shifts for inter-column diffusion

How It Works

ShiftRows cyclically shifts the bytes in each row of the state by a certain offset.

Row 0 No shift
Row 1 Shift left by 1
Row 2 Shift left by 2
Row 3 Shift left by 3

Why is ShiftRows needed?

Without ShiftRows, each column of the matrix would be encrypted independently from the others. MixColumns operates within a single column, SubBytes operates on each byte individually. Only ShiftRows mixes bytes between columns.

Together, ShiftRows and MixColumns achieve full diffusion in 2 rounds: changing one input byte affects all 16 output bytes.

Why exactly these shift amounts (0, 1, 2, 3)?

The shifts are chosen so that each byte of a column ends up in a different column after ShiftRows. If all rows were shifted by the same amount, it would just be a column rotation with no inter-column diffusion.

The values 0, 1, 2, 3 are the only set where 4 bytes from one column land in 4 different columns after shifting. This maximizes diffusion speed and is part of the "Wide Trail Strategy" — the design approach Rijndael's authors used for provable security.

MixColumns Transformation

Matrix multiplication in Galois Field GF(28)

How It Works

MixColumns treats each column as a polynomial over GF(28) and multiplies it with a fixed matrix:

[
02030101
01020301
01010203
03010102
]

Why this specific matrix?

The MixColumns matrix is an MDS matrix (Maximum Distance Separable) over GF(2⁸). This means it provides maximum diffusion: if at least one input byte differs, all four output bytes will differ.

The coefficients 01, 02, 03 were not chosen randomly — they are the smallest non-zero elements of GF(2⁸) for which multiplication is maximally efficient:

  • ×01 — identity operation (do nothing)
  • ×02 — left shift by 1 bit + conditional XOR with 0x1B (if high bit = 1). This is multiplication by x in the polynomial modulo the irreducible polynomial
  • ×03 — equals ×02 XOR ×01, i.e. (shift + conditional XOR) XOR original value

Why GF(2⁸) instead of normal arithmetic?

In normal arithmetic, multiplication overflows a byte (255 × 255 = 65,025). In GF(2⁸), the result always fits in 1 byte, and every operation is invertible. Addition is XOR (no overflow, no sign), multiplication is polynomial modulo the irreducible polynomial.

This makes AES algebraically elegant: all operations are defined in one field, all are invertible, and everything can be implemented efficiently in hardware.

AddRoundKey Transformation

XOR the state with the round key derived from the cipher key

How It Works

Each byte of the state is XORed with the corresponding byte of the round key.

XOR Operation
State[i,j] = State[i,j] XOR RoundKey[i,j]

Why XOR specifically?

  • Self-inverse: A XOR B XOR B = A. This means decryption uses the same operation — AddRoundKey is identical for encryption and decryption
  • Bijective: XOR loses no information. For any key K, the function f(x) = x XOR K is a bijection (one-to-one mapping)
  • Fast: A single CPU instruction. XOR of 128 bits is one operation on SIMD registers
  • In GF(2⁸), XOR = addition: XOR is addition in the Galois field GF(2⁸). So AddRoundKey is algebraically the addition of state and key

Why is AddRoundKey both first and last?

AES begins and ends with AddRoundKey. This is deliberate: without the initial AddRoundKey, the first SubBytes would be identical for all keys (nothing depends on the key). Without the final AddRoundKey, the last round could be "unwound" without knowing the key. Thus, key material "wraps" all rounds, making the cipher secure even against attacks targeting the outer rounds.

Key Expansion (Key Schedule)

Generating round keys from the original 128-bit cipher key

Why is Key Expansion needed?

AES-128 performs 10 rounds of encryption, and each round uses its own round key. Plus one more key for the initial AddRoundKey operation. That means 11 round keys (176 bytes) must be derived from a single 128-bit (16 byte) cipher key.

Why is this important for security?

Key expansion ensures that each round uses unique key material. This prevents attacks based on reusing the same key across rounds.

Cryptographic Properties

  • Non-linearity: The S-Box introduces non-linearity, protecting against linear cryptanalysis
  • Diffusion: Changing one bit of the key affects all round keys
  • Asymmetry: Rcon prevents identical round keys from being generated
  • Irreversibility: It is impossible to recover the original key from a single round key
